# Tubarão repository rules

- This copy is the Nova SBE classroom demo. Follow [NOVA-DEMO.md](docs/NOVA-DEMO.md) for runtime and integration rules. Use only loopback Supabase and synthetic data. Never connect or deploy this copy to the production services or reintroduce real payment, mail, map or social destinations.

- Read this file before significant changes. Use [BRAND.md](docs/BRAND.md) for visuals and copy, [PRODUCT.md](docs/PRODUCT.md) for business rules, and [TECHNICAL.md](docs/TECHNICAL.md) for current implementation and future architecture. These documents are the project source of truth; prototype behaviour and the older README do not override approved requirements.
- Preserve working design and functionality unless asked to change them. Prefer simple, small, reviewable changes; briefly explain large refactors before starting. Do not invent features or resolve open decisions by assumption.
- Keep the experience mobile first, fast, minimal, and appropriate to a real house party during one academic year.
- Preserve the original shark logo and its raw character. Do not modify, redesign, replace, or generate alternative logos without explicit instruction. Do not introduce AI-generated people without explicit instruction.
- Follow the black, bone-white, and Atlantic-blue brand system. Keep all public-facing copy in English and preserve the Tubarão accent in brand presentation.
- Never expose exact capacity, category inventory, or remaining ticket counts publicly. Exact figures belong only in authenticated, authorized internal views.
- Collect first name, last name, and email for purchase. Do not introduce phone-number or Instagram-username collection, guest accounts/passwords, or application/request-access/approval flows. Instagram following uses self-confirmation.
- Preserve the capacity and category rules in PRODUCT.md. Current defaults are not permanent constants; operational values must become editable data in the future backend product.
- Only authorized staff can confirm a simulated payment. A frontend claim alone never authorizes entry. Demo tickets remain individual, non-transferable and single-use at check-in.
- Keep the existing Supabase schema and RPCs. Report a concrete incompatibility before changing them. Server-side demo QR issuance requires admin-confirmed PAID. Only SUPER_ADMIN can download an issued QR for the current event. QR tokens are opaque and contain no personal, category, price or plaintext reservation data.
- Distinguish existing prototype behaviour, approved future requirements, and unresolved decisions in documentation. A documented future capability is not permission to implement it.

- Payment flow: RESERVED → simulated payment claim (PAYMENT_CLAIMED) → admin PAID or REJECTED. Keep the database-authoritative hold and claim deadlines and expiry rules. Public checkout never exposes a QR or a payment URL.
- EARLY/LATE pricing is configured per event; €8/€12 are editable new-event seeds. Do not introduce payment-cost calculations or split revenue totals. Revenue sums actual confirmed paid ticket prices. The local Supabase instance is authoritative for the demo. Browser storage is only a cache, never payment proof. Read price and deadlines from server responses; ignore old local demo sales/settings.

- Check-in must verify ADMIN/SUPER_ADMIN server-side, hash only the opaque QR token on the server, and use the atomic check_in_ticket/check_in_reservation RPCs with the authenticated actor. Only current-event PAID reservations qualify. Never admit based on browser state or generate non-paying QR tickets.

- Keep DEMO_SUPABASE_SECRET_KEY server-only. Every admin API must verify the HttpOnly session against admin_sessions and active admin_access_accounts server-side. SUPER_ADMIN has full management access; ADMIN is door/check-in only. No browser SDK, publishable key, Bearer token or browser session-token storage is needed. Do not add public reservation RLS access.

- Derive ticket tokens with versioned HMAC-SHA256 using the stable DEMO_TICKET_SIGNING_SECRET and reservation/event UUIDs. Store only the SHA-256 token hash, never plaintext tokens. Resends must reproduce and verify the same token; do not silently overwrite a mismatched hash.
- Keep the demo signing secret server-only. Issuance failure never reverses PAID. Record safe attempt metadata and allow explicit SUPER_ADMIN retry with the same QR. Record confirmed_by_access_id and preserve the original audit actor on retries.

- Pricing uses the additive 20261001_ticket_pricing.sql migration (manual deployment only). Database NOW() selects EARLY/LATE inside create_reservation; AUTO uses the dedicated early_price_ends_at, with equality selecting LATE and NULL remaining EARLY. Only SUPER_ADMIN may configure AUTO/EARLY/LATE overrides. Never use sales_close_at for pricing. Preserve each reservation’s stored amount_cents and pricing_tier, including recovery, claims and PAID. Checkout displays the stored amount for the simulated claim. Public countdowns are visual only, aligned with database server_now. Existing events backfill both prices from their legacy price; historical tiers stay NULL.

- Event-management mutations must use the service-only transactional SQL functions in supabase/migrations/20260928_admin_event_management.sql. Only SUPER_ADMIN can manage events and non-paying attendees. Preserve historical records. Never replace atomic activation or capacity checks with separate browser/server writes.
- Apply supabase/migrations/20260929_admin_access_auth.sql after event management and before cookie-auth deployment. It updates event authorization and check-in audit to checked_in_by_access_id while preserving historical columns. Never bypass its signature preflight guard.
- Access code → server-side scrypt verification → secure HttpOnly session → role authorization. Never hardcode/log plaintext codes or store plaintext sessions in the database. ADMIN accounts identify door devices/shifts, not named people.
- Keep the classroom follow self-confirmation and public brand handle without external navigation; never collect Instagram usernames. Link the concise /privacy.html notice beside reservation submission using acknowledgement, not an optional-consent checkbox.
- Event backup CSV is SUPER_ADMIN-only and an emergency/manual fallback. Export only the documented attendee columns, escape CSV/formula prefixes, and never include IDs, QR material or credentials. Downloading must not mutate attendance. The online QR backend remains necessary for live duplicate-check protection.
- ADMIN and SUPER_ADMIN may read LIVE ATTENDANCE via GET /api/admin/check-in?action=presence: checked-in PAID and non-paying people only, names/category/type/time and arrived-only KPIs. Never expose emails, IDs, unarrived guests, revenue or ticket-sales KPIs through presence. This does not grant non-paying management or additional check-in mutations. Keep presence polling independent of scanner operation.

- Reservation recovery: resume only a matching normalized name/surname/email/category for the active event, or revalidate a locally saved UUID/email through reservation-state. Never reset a resumed deadline or store browser payment proof. External payment confirmation is SUPER_ADMIN-only through confirm_external_payment and the existing payments function; apply 20260930_reservation_recovery.sql first. Preserve its atomic locks/capacity checks and audit, never replace it with separate REST mutations.

- Payment record deletion is SUPER_ADMIN-only, exact-ID and conditional on stored RESERVED/REJECTED/EXPIRED plus no payment, QR, sent-email or check-in markers. Keep every safety predicate in the actual DELETE; never substitute an unconditional delete after a read. Completed payment rows require PAID and non-null ticket_sent_at; preserve retry and the shared local issuance path.

- The separate delete-paid-ticket action permits SUPER_ADMIN hard deletion by exact ID only for stored PAID with checked_in_at IS NULL, repeated in the atomic DELETE. Issued QR/email markers do not block this explicit duplicate-removal path. Keep ordinary delete-record rules unchanged. No email, repricing, VOIDED state or fallback QR validation; refresh every affected list/KPI after success.

- Pricing migration 20261001_ticket_pricing.sql is already applied in production; never rewrite it. New 20261002_ticket_pricing_display_controls.sql adds two strict boolean preferences, default false: show_pricing_countdown and show_late_price_before_start. Only SUPER_ADMIN may edit them. They control EARLY presentation only; keep the muted Late section visible, hide its future amount unless enabled, never hide the active price, and never show a forced-mode countdown. They must never affect authoritative pricing or locked reservation amounts.

- PAID category correction uses SUPER_ADMIN-only change-category on the existing payments API and service-only admin_change_paid_category RPC (20261003_paid_category_correction.sql). Lock event advisory/event row before reservation row; require exact ID, PAID and no check-in. Count active MEN reservations/claims plus PAID against the cap. Change only category, never price/tier/identity/QR/payment timestamps; no automatic email. Existing QR signs IDs only. Manual resend reads the current category.

- Manual amount adjustment is the explicit SUPER_ADMIN exception to creation-time price locking. adjust-amount on the payments API calls admin_adjust_reservation_amount with exact ID and integer cents (1..100000); stored RESERVED/PAYMENT_CLAIMED/PAID only. The 20261004 migration atomically locks the row, records previous/new amount and actor in private reservation_amount_adjustments, and changes only amount_cents. Same amount creates no history. No automatic email, payment transfer, refund, tier/category/QR change or event repricing. Audit ID snapshots survive ticket deletion; history is not public or included in normal CSV.
